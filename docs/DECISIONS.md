# 設計判断ログ

経緯を知らずに「改善」すると過去の議論をやり直すことになるので、判断と理由、却下した案を残す。**却下案はユーザーが明示的に求めない限り再提案しない。**

## 計算・データ

### 朝一BIGランプは色カウントに含めない
ユーザー仕様。朝一の色は `morning` にだけ記録し、下線表示のみ。推測では BIG 回数を1回分減らす（白の誤計上防止）。一度「色カウントも減らす」修正を入れたが仕様誤解だったので差し戻した。

### BIG筐体ランプ `lampB` は直接確率として扱う
5色の合計が `1/blamp` と一致することを数値で確認。以前の逐次抽選変換は誤りだった。

### 合算(gas)の尤度も総合推測に掛ける
BIG・REG と情報が重複するのは承知の上。ユーザーが重複前提で重みを調整しているため。

### ニューキングⅤ 設定Vのサイドランプ
既存ツールとの乖離調査の結果、「完全均等（旧設定6型）」ではなく寒色寄りの振り分けを採用。合計が101%になっていたため、黄と赤を0.5%ずつ減らして 26.5 / 19.5 / 28.5 / 25.1 / 0.4 に確定。

### スプレッドシートは生データのみ保存、推測は読み込み時に計算
要素調整を変えたら過去データにも反映させたい、というユーザー要望。保存時に推測結果や復元用JSONは書かない（末尾4列は空欄）。

### 信頼度ランクの虹は確定示唆のみ
「どれだけ尤度が高くても確定示唆がなければ最高止まり」。

### 大当たり履歴の管理方式
- BIG/REG を押した瞬間に記録を作る（押したのに記録されないのはおかしい、という指摘）
- `cur.g` は「打ち始め＋記録合計＋ハマり」。記録合計で上書きする方式は現在ハマりが消えるので不可
- `_lastHitTotal`（前回合計との差分）方式は新規当選時に二重加算するので廃止し、編集セッション単位で `hitTailG` を固定する方式にした
- 削除時の区間は新しい側へ繰り入れる（古い側は誤り。一度間違えた）

### 差枚係数
ドラゴン・キングは実測で調整（docs/CALIBRATION.md）。ニューキングⅤは構造的に合わないので放置。

## UI

- 分析画面の入口は「設定推測」ヘッダーのタップ（長押し→タップに変更済み）
- BIG/REG 減算時の削除確認UIは廃止（即削除）。修正は当選履歴から行う
- 緑の「取込」通知バナーは邪魔なので廃止済み（受信箱機能自体も削除）
- ボタンが大きすぎる／ヘッダーが高すぎる、という指摘が繰り返しあった。サイズを決めるときは `.hist-filter-btn` とメイン画面ヘッダー(40px)に合わせる

## 却下・撤去した案（再提案しない）

| 案 | 結果 | 理由 |
|---|---|---|
| GAS 受信箱による背面タップ連携 | 実装後に**全撤去** | 実戦でベルが約80回欠落（1/7.5→1/8.5）。通信不確実性。コードもGAS側APIも削除済み |
| ショートカットで localStorage / ファイルを直接書く | 不可 | iOS Safari の JS はファイルアプリや他アプリ領域にアクセスできない |
| ファイル選択で自動加算＋ショートカットでリセット | 見送り | 画面遷移2回で手入力より遅い |
| 背面タップのトリプルタップでリセット | 不採用 | 誤タップする。リセットはコントロールセンターに置いた |
| Web Bluetooth で物理ボタン連携 | 不可 | iOS Safari 非対応 |
| BLE キーボード化した ESP32 物理ボタン | 保留 | 唯一「他アプリ中も確実に自動反映」できる案。内部カウント保持＋F13〜F24キーで送信する設計まで検討済み |
| ネイティブアプリ化 | 不採用 | 開発者登録費・審査に見合わない |

## 現在の運用

他アプリを見ながらのカウントは、iOS ショートカット（背面ダブルタップで `Shortcuts/count.txt` を+1、コントロールセンターからリセット）で数え、あとで機種名長押しの「まとめて加算」で入力する。手順は docs/SHORTCUTS.md。
